# Migration plan

1. **Define scope and risk:** URL changes? domain change? HTTPS? content/template rewrite? language changes? Higher risk when URLs, content and platform all change at once; split into phases when possible.
2. **Baseline before touching anything:** full crawl of the live site (URL, status, canonical, title, meta robots, internal links, depth), XML sitemaps, top landing pages and conversions from analytics, Search Console performance and indexing reports, backlink profile of top linked URLs (from available tools), server log sample, Core Web Vitals field data. Store as dated files.
3. **URL mapping:** map every old indexable URL to the most relevant new URL (1:1 where equivalent). Group by rule (pattern) plus explicit exceptions. Avoid mapping everything to the homepage or a generic category; use 410 for content intentionally removed with no replacement. Include images/PDF assets that have traffic or links, query-string variants worth keeping, and trailing-slash/case variants.
4. **Redirect rules:** 301/308 server-side, single hop, no chains/loops (test the map for chains after composing with existing redirects, protocol/host rules and trailing slash rules), preserve language folders, handle parameters. Keep rules maintainable (patterns in config for large sets, a lookup table for exceptions) and performant.
5. **Staging tests:** staging is protected by authentication and `noindex`; crawl staging, run the redirect map against the old URL list and check each returns the expected final status and target; compare titles/headings/content parity, canonicals, structured data, hreflang, internal links, sitemaps, robots, analytics tags, performance.
6. **Launch checklist:** remove staging `noindex`/disallow and authentication on the new production; verify robots.txt and meta robots in production; new sitemaps live and submitted; old sitemap kept temporarily so crawlers can discover redirects; canonicals and internal links point to new URLs; HTTPS and HSTS settings reviewed; analytics and Search Console properties verified for new host(s); domain changes: use the Search Console change-of-address tool where documented as applicable (verify conditions); update key external profiles and high-value backlinks where possible; DNS TTL lowered beforehand; rollback plan and owner named.
7. **Immediately after launch:** crawl production, check redirects, status codes, robots, canonical, sitemap health; verify server capacity and error rates; check indexing status of key URLs via URL Inspection.
8. **Keep redirects** long term (commonly at least a year, [Practice]) and do not shut down the old domain early.
9. **Rollback criteria:** pre-agree (for example widespread 5xx, incorrect robots/noindex, redirect rules broken) and keep the previous system recoverable for the agreed period.
10. **Approval:** production changes (DNS, redirects, robots, noindex removal) need explicit approval naming the environment.
