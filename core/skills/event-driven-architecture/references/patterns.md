# Event-driven patterns

- **Commands vs events:** a command asks one handler to do something (can fail, has a recipient); an event states a fact that happened (many subscribers, no reply). Name events in past tense with domain meaning (`OrderPaid`), not CRUD noise.
- **Transactional outbox:** write the business change and an outbox row in one DB transaction; a relay (poller or change-data-capture) publishes rows and marks them sent; publishing is at-least-once, consumers dedupe. Avoid "dual writes".
- **Idempotent consumers:** keep a processed-events table keyed by event ID (and consumer name) written in the same transaction as the side effect, or make the operation naturally idempotent (upsert, set-state, conditional update by version).
- **Retries and failures:** classify errors (transient vs permanent); exponential backoff with jitter; max attempts; dead-letter queue with metadata (error, attempts, original message); runbook and tooling to inspect and replay; alert on DLQ growth.
- **Ordering:** broker-level ordering is per partition/queue key; choose the key (aggregate ID) so related events stay ordered; handle out-of-order arrival with versions/sequence numbers and ignore stale updates; avoid global ordering needs.
- **Sagas / process managers:** long-running business transactions as a sequence of local transactions with compensating actions; orchestration (a coordinator with explicit state) is easier to reason about than choreography for complex flows; persist saga state; timeouts and manual intervention paths; compensation can fail, so design for it.
- **CQRS and event sourcing:** separate read models fed by events when read/write needs diverge; event sourcing (state as an event log) adds major complexity (versioning, replay, snapshots): adopt only for a clear audit/temporal need.
- **Delivery semantics:** at-most-once (may lose), at-least-once (may duplicate; default), "exactly-once" is achieved by idempotent processing plus transactional guarantees within a system, not magic across systems.
- **Broker selection (trade-offs, verify current features):** database-backed queue (simple, transactional with data, limited throughput), Redis-based (fast, durability limits), RabbitMQ-class (routing, acks), SQS-class managed (simple ops, limited ordering options), Kafka-class log (high throughput, replay, ordering by partition, higher operational cost). Choose by volume, ordering, replay, team skills and ops capacity.
- **Backpressure and scaling:** consumer concurrency limits, prefetch tuning, autoscale on queue age, protect downstream dependencies with rate limits and circuit breakers.
- **Synchronous alternative:** if a flow needs an immediate answer, has low volume and few consumers, a direct call (with timeouts and retries) is simpler and often better.
